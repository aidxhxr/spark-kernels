# RTX 5090 hardware sheet (primary target)

The repo started as a DGX Spark project, but the machine I actually have is an RTX 5090, so
that is what the defaults build for and what the first results will come from. The GB10 stays
as the secondary target ([GB10.md](GB10.md)) and gets benchmarked when the Spark arrives. Same
kernels, same programming model, two memory systems 6.5× apart.

These are the numbers the roofline and the "% of peak" columns in `RESULTS.md` are based on.
Nothing has been measured on this card yet; anything I do not have a source for is marked
**TBD — measure** with the command that produces it.

The 213 TFLOPS bf16 figure in [GB10.md](GB10.md) is a community measurement on the GB10 only.
I do not scale it by core count to get a 5090 number: tensor-core throughput at 1.8 TB/s is
exactly the thing this repo is supposed to measure, not assume. Until a measured peak exists,
`scripts/make_results_table.py` and `scripts/roofline.py` print "—" for "% of peak" on the
`hgemm` rows; pass `--bf16-peak=<TFLOPS>` to either script once there is a number. The
"% of cuBLAS" column does not depend on it.

Why CUDA 13.0 and not 12.8: the bench banner uses a CUDA 13 device-attribute API, and the
secondary target (`sm_121`) is unknown to anything older. One toolkit for both machines.

## Ridge points

Arithmetic intensity at which a kernel stops being memory-bound:

| ceiling | RTX 5090 | GB10 |
|---|---|---|
| fp32 CUDA cores | 104.8 TFLOPS ÷ 1,792 GB/s ≈ **58.5 FLOP/byte** | 31 ÷ 273 ≈ 114 |
| bf16 tensor cores | **TBD** (needs the measured bf16 peak) | 213 ÷ 273 ≈ 780 |

What that means here:

- A 4096³ GEMM has an intensity of `2n/12` ≈ 683 FLOP/byte in fp32 and ≈ 1,365 in bf16. On the
  5090 that is more than 10× past the fp32 ridge, so `sgemm` is compute-bound with a lot of
  margin, and a kernel that reuses data badly is punished less than on the GB10.
- The row-wise kernels (RMSNorm, SwiGLU, softmax) sit at roughly 1–5 FLOP/byte, far left of
  the ridge on both machines. They can never do better than the memory system, so they are
  reported as **% of DRAM bandwidth** (1,792 GB/s here).
- Fusion: GDDR7 at 1.8 TB/s is much closer to HBM-class bandwidth than LPDDR5X is, so the
  absolute time saved per removed pass is about 6.5× smaller than on the GB10. `add_rmsnorm`
  and `swiglu` still remove whole passes and launches, so the *ratio* against the unfused
  sequence should survive; the milliseconds shrink. On the 5090, launch overhead is a larger
  share of what fusion buys.

## Same programming model as the GB10

`sm_120` and `sm_121` are the same family (table in [GB10.md](GB10.md#sm_121-is-not-sm_100)):
`mma.sync` / WMMA and `cp.async` work, `tcgen05` / TMA / thread-block clusters do not. No
source changes between the two machines. What differs:

- the arch flag (`120` vs `121`);
- the tuning constants, which were reasoned for 48 SMs and 273 GB/s. They are correct on both
  machines, just not necessarily optimal on this one. To re-derive after the first run:
  - `hgemm`: 128×128×32 block tile, +8-element padding against bank conflicts, 8 warps per tile;
  - `sgemm`: 128×128×8 block tile with an 8×8 register tile;
  - the `cols > 8192` (rmsnorm) and `cols > 4096` (softmax) crossovers to the block-per-row
    variants.

  Each `docs/design/*.md` has an "RTX 5090 notes" section with what I expect to move and what
  to look at in Nsight Compute. Those are expectations, not results.
- grid sizes for the grid-stride kernels come from `multiProcessorCount` at runtime, so they
  follow the SM count (170 here) without a rebuild.

Every kernel stays ≤ 48 KB static shared memory on both targets, so no `cudaFuncSetAttribute`
opt-in is needed.

## Build flags used here

`120` is the default everywhere, so none of these flags need to be spelled out:

```bash
# CMake (bench binaries + static lib); CMAKE_CUDA_ARCHITECTURES defaults to 120
make build                      # same as: make build ARCH=120
make build ARCH=121             # DGX Spark
make build ARCH="120;121"       # one build for both

# PyTorch extension; setup.py pins sm_120 when TORCH_CUDA_ARCH_LIST is unset
pip install -e . --no-build-isolation
TORCH_CUDA_ARCH_LIST="12.1" pip install -e . --no-build-isolation   # DGX Spark
```

`-lineinfo` is on by default so Nsight Compute can map stalls back to source lines without
the cost of `-G`.

## Verify on your box

```bash
nvidia-smi                                     # driver + "NVIDIA GeForce RTX 5090", 32 GB VRAM listed
nvcc --version                                 # must be 13.x
/usr/local/cuda/extras/demo_suite/deviceQuery  # CUDA Capability 12.0, 170 multiprocessors, L2 size
python3 -c "import torch; print(torch.cuda.get_device_name(), torch.cuda.get_device_capability(), torch.version.cuda)"
```

Expected: `NVIDIA GeForce RTX 5090 (12, 0) 13.x`. Unlike the GB10, memory is discrete, so
`nvidia-smi` shows VRAM usage normally and `free -h` tells you nothing about the GPU.

## Measuring on a GeForce card

Things that do not matter on the Spark and do here:

- **Boost and throttle.** A 575 W card ramps its clocks up under load and pulls them back when
  it hits a power or thermal limit. Each bench spins its first kernel for ~300 ms before timing
  anything, so the clocks have ramped, then warms every timing loop with 5–10 launches
  (`--warmup=N` overrides the count, `--warmup=0` also skips the ramp). Every JSON row carries
  `min_ms` next to the median; if the two diverge, the run was throttling or still ramping.
  `nvidia-smi -q -d PERFORMANCE` shows the active throttle reasons. For the tightest numbers
  lock the clocks with `sudo nvidia-smi -lgc <MHz>,<MHz>` (take the max from `nvidia-smi -q -d
  CLOCK`) and undo it with `sudo nvidia-smi -rgc`.
- **Display.** If the 5090 drives a monitor, the compositor steals time slices and VRAM
  bandwidth. Run headless, or put the display on a second GPU / the iGPU.
- **Profiling permissions.** Nsight Compute hardware counters on GeForce need admin rights.
  Either run `scripts/profile_ncu.sh` as root, or set the nvidia module option
  `NVreg_RestrictProfilingToAdminUsers=0` (e.g. in `/etc/modprobe.d/`) and reboot.
- **Memory.** Every bench allocates device memory only; the largest is `bench_bandwidth` with
  2 × 1 GiB. 32 GB is never a constraint and nothing crosses PCIe inside a timing loop.
- **Which device.** Bench JSON rows carry a `device` field. The results scripts use it to pick
  this card's ceilings, and they refuse a `results/` directory that mixes machines: move the
  old `*.json` aside before benchmarking the Spark.
- **Provenance.** `make env` (`scripts/gpu_env.sh`) prints the driver, P-state, clocks against
  their maxima, power limit, throttle reasons and whether a display is attached, and warns
  about the last two. `scripts/run_all.sh` saves it as `results/env.txt` before building, so a
  set of numbers can later be matched to the state the card was in.

## Measuring your own ceiling

`bench_bandwidth` (in `build/`) copies a large fp32 array and reports achieved GB/s. That
measured number is the realistic roof for the row-wise kernels; expect it below the
1,792 GB/s spec (a copy pays for a read and a write stream, and nothing reaches the
theoretical figure), so treat "% of 1,792 GB/s" as conservative. How far below: TBD — this is
the first thing `make bench` will tell me.
